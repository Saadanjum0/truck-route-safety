# Safe Truck Route Planner

React + Django app that helps a truck driver pick the safest route between two places, based on
the weather forecast along each route, the load weight, and travel time.

**Live app:** https://truck-route-safety.vercel.app

## What it does

1. The driver enters origin, destination, departure date/time, load weight and a sampling interval (10 / 25 / 50 miles).
2. The backend geocodes both places and gets **3 route options** from OSRM.
3. Each route is cut into **checkpoints every N miles**. Each checkpoint gets an **ETA** (departure time + OSRM's
   cumulative driving time to that point).
4. Each checkpoint gets the **hourly forecast for its ETA hour** (wind, rain, snow) and a **risk level**
   from the rules below.
5. The routes are ranked and **one is recommended**, with the reason it won.
6. The map shows all routes, colour-coded checkpoints (click one for ETA, forecast and risk), route summaries
   (sidebar cards and hover tooltips), and a **weather heatmap over the trip corridor** with a **0–48 h forecast slider**
   (play/pause; layers: overall risk, wind, rain, snow).

## Risk rules (`backend/planner/risk.py`)

| Condition | Low | Moderate | High | Severe | No Travel |
|---|---|---|---|---|---|
| Wind (mph) | < 25 | 25–34 | 35–44 | 45–54 | ≥ 55 |
| Rain (in/hr) | < 0.10 | 0.10–0.25 | 0.25–0.50 | 0.50–1.00 | > 1.00 |
| Snow (in/hr) | < 0.5 | 0.5–1.0 | 1.0–2.0 | 2.0–3.0 | > 3.0 |

- A checkpoint's level is the **worst** of the three conditions.
- Load rules: ≥ 55 mph is No Travel for any load; 45–54 mph with > 30,000 lb is **No Travel**; 35–44 mph with > 40,000 lb is **Severe**.
  Load rules can only raise a level, never lower it.
- Where two bands share an edge (e.g. rain 0.25), the value goes to the **higher** band. The exception is the No Travel
  edge, where the table says "> 1.00" / "> 3.0", so exactly 1.00 in/hr of rain is Severe.

**Recommendation** (`rank_key`), in order:
1. Fewest No Travel miles. These count as "worse than Severe", so a route through No Travel weather never beats one that only has Severe.
2. Fewest Severe miles.
3. Fewest High miles.
4. Lowest average risk (distance-weighted, 0 = Low … 4 = No Travel).
5. Shortest travel time.

**Miles at each level:** each checkpoint stands for the road halfway to its neighbouring checkpoints, so a segment between
a Low and a High checkpoint counts half Low and half High. If even the best route crosses No Travel weather, the app
shows a warning to delay departure.

## Architecture

```
frontend/  React 18 + Vite + react-leaflet (OpenStreetMap tiles)
  src/App.jsx      form, recommendation, route cards
  src/MapView.jsx  routes, checkpoints, corridor heatmap, forecast slider
backend/   Django 5.2 (no database: stateless JSON API)
  planner/risk.py      risk rules, route summary and ranking (pure functions)
  planner/services.py  geocoding, routing, checkpoint sampling, weather, pipeline
  planner/views.py     POST /api/plan, input validation
  planner/tests.py     rule, ranking and sampling tests
api/index.py  Vercel entry point (Django WSGI as a serverless function)
```

Third-party APIs, all free and keyless:

| Purpose | API |
|---|---|
| Geocoding | Nominatim (OpenStreetMap) |
| Routing | OSRM public server (`alternatives=3`, per-segment distance/duration annotations) |
| Weather | Open-Meteo hourly forecast (`wind_speed_10m` in mph; `rain + showers` and `snowfall` in inches per hour) |

### Design notes
- **3 routes:** OSRM often returns only 1–2 alternatives. The rest are generated by routing through via points offset
  sideways from the midpoint of the trip. A candidate is kept only if it is at most 1.5× the fastest time and differs
  from the existing routes (less than 85% overlap on a ~1 km grid).
- **ETAs** use OSRM's per-segment durations, so a checkpoint after slow city driving gets a later ETA than a straight
  distance/speed estimate would give. The forecast hour used is the one nearest the ETA.
- **One forecast request for everything:** checkpoints and heatmap cells are snapped to a 0.1° grid (~7 mi), deduplicated,
  and fetched in batches of 100 locations in parallel. Results are cached in memory for 30 minutes.
  Open-Meteo counts each location as one call against a per-IP limit, so this keeps a typical plan at ~100–250 calls.
- **Heatmap:** the corridor is a regular lat/lon grid (≤ 100 cells within one cell of any route). Weather for all
  49 hours comes back with the plan, so moving the slider makes no network calls. Each hour is drawn as a tiny canvas
  image (one pixel per cell) and stretched over the map, and the browser's smoothing turns it into a continuous field.
  Colours follow a continuous 0–4 risk index whose integer steps are the table thresholds, so the colours match the legend exactly.
  This avoids the false "hot spots" that density heatmaps such as leaflet.heat create where points overlap.
- **Times:** the browser sends the departure as UTC; ETAs are shown in the viewer's local time zone.

### Known limitations
- OSRM's public server uses a **car** profile: it ignores truck restrictions (height, weight, hazmat) and car speeds make ETAs a little optimistic.
  A production version would use a truck-aware router (e.g. GraphHopper, HERE or ORS `driving-hgv`).
- ETAs do not include rest breaks or hours-of-service limits.
- Wind uses sustained 10 m wind speed, not gusts.
- Free public APIs have rate limits. If one is hit, the app shows the provider's message ("try again in a minute").
- Departure must be within the next 7 days (forecast range).

## Run locally

Requirements: Python 3.10+ and Node 18+.

```bash
# backend (http://127.0.0.1:8000)
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cd backend && ../.venv/bin/python manage.py runserver

# frontend (http://localhost:5173, proxies /api to Django)
cd frontend && npm install && npm run dev

# tests
cd backend && ../.venv/bin/python manage.py test planner
```

## API

`POST /api/plan`

```json
{ "origin": "Chicago, IL", "destination": "Denver, CO", "departure": "2026-10-19T14:00:00Z",
  "load_lb": 42000, "interval_mi": 25 }
```

The response contains `routes[]` (geometry, `checkpoints[]` with ETA, wind/rain/snow, level and reasons, plus a `summary`
of miles by level and average risk), the `recommended` route index with its `reason`, an optional `warning`, and
`heatmap` (grid points and a 0–4 risk index per hour for each of the overall/wind/rain/snow layers).

## Deploy

The app is hosted on Vercel as one project: the Vite build is served as static files and Django runs as a Python function
behind `/api/*` (see `vercel.json`). To deploy: `vercel deploy --prod`.
